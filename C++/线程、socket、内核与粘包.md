## 1. 三个基础概念

### 1.1 线程（thread）

- **是什么**：程序执行的最小单位，也是 CPU 调度的对象。一个进程里可以有多个线程，它们共享同一份地址空间和文件描述符。
- **与进程的区别**：进程是资源分配的单位（有独立地址空间），线程是调度的单位（共享进程的资源）。所以线程切换比进程切换便宜，但一个线程把内存写坏，整个进程都会跟着崩。
- **线程自己独占什么**：栈、寄存器现场、线程局部存储；**共享**堆、全局变量、打开的文件和 socket。
- **在 C++ 里**：用 `std::thread` 创建线程；正因为内存是共享的，读写共享数据必须加锁（`std::mutex`），否则就是数据竞争（data race）。
- 一句话：**线程是同一个程序内部的并行执行流。**

### 1.2 内核（kernel）

- **是什么**：操作系统的核心，运行在内核态（特权态），负责 CPU 调度、内存管理、文件系统、网络协议栈、设备驱动等。
- **用户态 / 内核态**：普通程序运行在用户态，不能直接操作硬件；需要网络、文件这类资源时，要通过**系统调用**（syscall）陷入内核，由内核代为完成。
- **为什么要这样分**：隔离与安全。如果任何程序都能直接改内存、直接驱动网卡，系统早就乱套了。
- 一句话：**内核是用户程序与硬件之间的"总管家"。**

### 1.3 socket

- **是什么**：操作系统提供的网络编程接口，同时也是"一条连接"在程序里的句柄（本质是一个文件描述符）。
- **谁在干活**：socket 由内核维护。程序调用 `socket()` / `bind()` / `connect()` / `send()` / `recv()`，其实是**委托内核的网络协议栈**去收发数据。
- **怎么标识一条连接**：五元组——协议、源 IP、源端口、目的 IP、目的端口。
- **最容易被忽略的一点**：数据不是程序直接从网卡拿的。网卡收到的数据先由内核放进这个 socket 的**接收缓冲区**，程序调用 `recv` 时才把数据拷到自己的内存里。
- 一句话：**socket 是用户程序与内核网络协议栈之间的"插座"。**

三者的关系：

| 概念 | 所在位置 | 一句话 |
| --- | --- | --- |
| 内核 | 内核态，操作系统的核心 | 管硬件与资源的"总管家" |
| socket | 内核维护的接口，句柄交到用户程序手里 | 用户程序与网络协议栈之间的插座 |
| 线程 | 进程内部的执行流 | 真正去调用 `send` / `recv` 的"人" |

## 2. TCP、UDP 与"粘包"到底是什么

### 2.1 先分清：TCP 是字节流，UDP 是数据报

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 连接方式 | 面向连接（三次握手） | 无连接 |
| 数据形态 | **字节流**，没有消息边界 | **数据报**，一条是一条 |
| 可靠性 | 按序到达、不丢不重 | 可能丢包、乱序、重复 |
| 消息边界 | 不保留，要靠应用层自己划分 | 天然保留：一次 `sendto` 对应一次 `recvfrom` |

### 2.2 "粘包"到底是什么

先说结论：**TCP 里根本没有"包"这个概念，也没有"粘"这个动作。** TCP 只认字节，不认消息。所谓粘包，其实是**应用层用"一次 send 对应一次 recv"的假设去解析数据，结果对不上**：

- 两次 `send` 的数据被一次 `recv` 全读回来 —— 看起来"粘"在一起
- 一次 `send` 的数据要两次 `recv` 才读完 —— 看起来"被拆开"

为什么会这样：

1. **发送方会攒**：Nagle 算法默认把小块数据攒一攒再发，以减少网络上的小包数量；内核的发送缓冲区本来就是按字节排队的。
2. **网络会拆**：受 MTU / MSS 限制，一大段数据会被拆成多个 TCP 段传输，到对端再拼回字节流。
3. **接收方读多少不由 send 决定**：`recv` 一次读走多少字节，取决于"内核接收缓冲区当前有多少数据"和"你传进去的 buf 有多大"，与发送方调了几次 `send` 毫无关系。

所以粘包不是 bug、也不是错误状态，而是**"字节流 + 缓冲区"这套机制的自然结果**；真正缺的是**应用层自己的消息边界**。

### 2.3 解决办法：应用层自己划边界

| 方案 | 做法 | 例子 |
| --- | --- | --- |
| 长度前缀（最常用） | 消息头里带长度字段，先读头再读正文 | 自定义协议、protobuf 分帧 |
| 固定长度 | 每条消息长度固定 | 定长结构体 |
| 分隔符 | 用特殊字符标记消息结束 | HTTP 头用 `\r\n\r\n`、文本协议用 `\n` |
| 自描述格式 | 格式自身携带边界信息 | HTTP chunked、TLV |

C++ 里的典型写法（长度前缀 + 接收缓冲区累积）：

```cpp
std::vector<char> buf;                     // 累积收到的字节
char tmp[4096];
for (;;) {
    ssize_t n = ::recv(fd, tmp, sizeof(tmp), 0);
    if (n <= 0) break;                     // 对端关闭或出错
    buf.insert(buf.end(), tmp, tmp + n);

    for (;;) {                             // 循环取出所有完整消息
        if (buf.size() < 4) break;         // 连长度头都没收全
        uint32_t len = 0;
        std::memcpy(&len, buf.data(), 4);
        len = ntohl(len);                  // 网络字节序转本机字节序
        if (buf.size() < 4 + len) break;   // 正文还没收全，等下一次 recv
        handle_message(buf.data() + 4, len);
        buf.erase(buf.begin(), buf.begin() + 4 + len);
    }
}
```

要点：**绝不要假设一次 recv 就是一条完整消息**；先把字节攒进缓冲区，再按边界循环切分。

顺带一提：用 `TCP_NODELAY` 关掉 Nagle 算法可以降低小包延迟，但它只改变"攒不攒"，**并不能解决边界问题**——边界只能靠应用层协议来划。

### 2.4 UDP 会粘包吗

- **严格说不会**：UDP 保留消息边界，一次 `sendto` 对应一次 `recvfrom`（前提是缓冲区足够大）。
- 但有两种容易被误认为"粘包"的现象：
  1. **截断**：如果应用给的缓冲区比数据报小，超出的部分会被直接丢弃，不会留到下一次 `recvfrom`——看起来像"丢数据"。
  2. **缓冲区排队**：UDP 的接收缓冲区里同样是排队的，你这次只读走一个，剩下的还在缓冲区里等着——但它们仍然是**互相独立**的报文，不会合并。
- 所以两者的"额外工作"正好相反：**TCP 要自己处理边界，UDP 要自己处理丢包、乱序、重复。**

### 2.5 一句话总结

- 粘包 = 应用层按"一次 send = 一次 recv"解析 TCP 字节流造成的对不上，根因是 **TCP 是流、边界要应用层自己划**。
- UDP 天生有边界，所以不粘包，但要自己面对不可靠。

## 3. 程序是怎么被启动的

### 3.1 Python 里的"main 函数"长什么样

先说一个容易踩的点：**Python 没有 C/C++ 那样的入口函数**。解释器拿到脚本后是从第一行开始**顺序执行**的，"入口"就是文件开头。所谓 Python 的 main，只是一套约定俗成的写法：

```python
import sys

def main(argv):
    print("真正的逻辑写在这里：", argv[1:])

if __name__ == "__main__":
    main(sys.argv)
```

三个关键点：

1. **`__name__` 是什么**：每个模块都有一个内置变量 `__name__`。
   - 直接运行这个文件（`python demo.py`）时，`__name__` 等于字符串 `"__main__"`
   - 被别的模块 `import` 时，`__name__` 等于模块名（例如 `demo`）

   本机实测（Python 3.12.7）：

   | 运行方式 | 打印出的 `__name__` | `main()` 是否执行 |
   | --- | --- | --- |
   | `python demo.py hello 42` | `__main__` | 执行，参数为 `['hello', '42']` |
   | `import demo` | `demo` | 不执行 |

2. **`if __name__ == "__main__":` 的作用**：让这段代码**只在直接运行时执行**，被 import 时不执行——避免"导入即开跑"的副作用（连数据库、跑测试、打印日志）。
3. **`main` 这个名字没有任何魔法**：叫 `run()`、`start()` 都行，纯粹是大家从 C 那里沿用来的习惯。参数也要自己定，Python 不会自动把命令行参数喂给你，得自己从 `sys.argv` 里取（或者用 `argparse`）。

顺带一句：`sys.argv[0]` 是脚本路径，真正的参数从 `sys.argv[1]` 开始——这和 C 里 `main(argc, argv)`、`argv[0]` 是程序名的习惯是一致的。

### 3.2 在 PowerShell 里敲 ping，是怎么连到 exe 并启动的

输入 `ping 127.0.0.1` 之后，发生的事情可以拆成三步。

**第 1 步：命令解析——"ping" 是谁？**

PowerShell 按 **别名 → 函数 → cmdlet → 外部程序**的顺序查找 `ping`：

- `ping` 不是别名、不是函数、也不是 cmdlet，于是被当作**外部程序**；
- 它在 `PATH` 环境变量列出的目录里找 `ping` 加上 `PATHEXT` 后缀名的文件。本机的 `PATH` 里含 `C:\WINDOWS\system32`，`PATHEXT` 里含 `.EXE`，于是命中 `C:\Windows\System32\PING.EXE`。

可以自己查证：

```powershell
Get-Command ping        # CommandType=Application，Source=C:\Windows\System32\PING.EXE
where.exe ping          # 列出 PATH 中所有匹配的可执行文件
(Get-Command ping).Path # 只看路径：C:\Windows\System32\PING.EXE
```

**第 2 步：创建进程——参数是怎么传过去的？**

PowerShell 通过 Windows API `CreateProcess` 启动 `PING.EXE`（.NET 里就是 `Process.Start` 底层做的事）：

- **新进程**：任务管理器里会多出一个 `PING.EXE` 进程，它的父进程是 PowerShell；
- **地址是通过命令行字符串传的**：`CreateProcess` 有一个参数 `lpCommandLine`，PowerShell 把要执行的文件和参数拼成类似 `"C:\Windows\System32\PING.EXE" 127.0.0.1` 这样一条命令行。它**不是**通过环境变量、也不是通过标准输入传的；
- **从命令行到 argv**：`PING.EXE` 的启动代码（C 运行时 CRT）会把这条命令行拆分成 `argc` / `argv` 数组，再交给它的入口 `main(argc, argv)`：
  - `argv[0]` —— 程序名（ping）
  - `argv[1]` —— `"127.0.0.1"`，也就是你要 ping 的地址
  - 如果是 `ping -n 4 127.0.0.1`，就是 `argv = ["ping", "-n", "4", "127.0.0.1"]`，由 ping.exe 自己去解析哪些是选项、哪个是地址
- **标准输入/输出/错误三个句柄**也由父进程在创建时交给子进程（默认继承当前控制台），所以你在 PowerShell 窗口里看到的 ping 输出，其实是子进程写出来的。

**第 3 步：ping.exe 自己干活**

它解析 `argv` 里的选项（`-n` 次数、`-w` 超时、`-t` 长 ping 等）和目标地址，把域名交给 DNS 解析成 IP，再通过**套接字**请内核网络栈发出 ICMP Echo Request、等待 Echo Reply，最后打印统计结果。这一段正好接上第 1 节：用户态程序（ping.exe）→ 系统调用 → 内核协议栈 → 网卡。

**两个实践上的坑**

- 参数之间用空格分隔，**含空格的参数要加引号**，例如 `ping -n 4 "my host"`；PowerShell 对引号的解析规则和 cmd 不完全一样，传复杂参数时可以先把可执行文件全路径写出来，或用 `--%` 让 PowerShell 停止解析后面的内容。
- 如果 `PATH` 里有多个同名程序，先被找到的那个生效（`where.exe` 能看到全部候选）。这也是"为什么我明明装了另一个版本，敲命令却还是老版本"的常见原因。

本机实测结果：

```text
Get-Command ping  →  PING.EXE   CommandType=Application   Version=10.0.26100.8115
                     Source=C:\Windows\system32\PING.EXE
where.exe ping    →  C:\Windows\System32\PING.EXE
```

## 4. 对象的两种创建方式、重载与虚函数

### 4.1 `类名 变量名;` 与 `new` 的区别

先澄清一个术语：`Vec2 a(1, 2);`严格说是**自动存储期（栈上）**对象，C++ 里"静态"通常专指 `static` / 全局对象（静态存储期）。不过口语里常把"不用 new 直接定义"叫"静态声明"，意思是**生命周期由作用域自动管**。下面按这个约定来对比。

```cpp
Vec2  a(1, 2);                          // 栈上：离开作用域自动析构
Vec2* p = new Vec2(3, 4);               // 堆上：必须自己 delete
auto  q = std::make_unique<Vec2>(5, 6); // 堆上，但由智能指针自动管理（推荐）
```

| 对比项 | `类名 变量名;`（栈 / 自动存储期） | `new 类名(...)`（堆 / 动态存储期） |
| --- | --- | --- |
| 内存位置 | 栈 | 堆（自由存储区） |
| 生命周期 | 由**作用域**决定，自动构造、自动析构 | 由**程序员**控制，`delete` 之前一直活着 |
| 访问方式 | 直接用 `a.member`、`a.method()` | 通过指针 `p->member`、`p->method()` |
| 释放 | 自动 | 手动 `delete`，或交给智能指针 |
| 能否跨函数存活 | 不能（返回它的指针/引用会变成悬空指针） | 能 |
| 分配开销 | 极小（只是移动一下栈指针） | 较大（走分配器，必要时进内核） |
| 大小限制 | 受栈大小限制（通常几 MB） | 受进程可用内存限制 |
| 典型风险 | 栈溢出、返回局部对象的引用 | 内存泄漏、悬空指针、重复释放 |

实测（MSVC 2022 / x64）能直接看到生命周期差别：

```text
1) 栈上对象
  [构造] Vec2(1, 2)
  a.len2() = 5
  [析构] Vec2(1, 2)          ← 离开作用域那一刻自动析构
2) 堆上对象
  [构造] Vec2(3, 4)
  p->len2() = 25
  [析构] Vec2(3, 4)          ← delete 时才析构
3) 智能指针
  [构造] Vec2(5, 6)
  q->len2() = 61
  [析构] Vec2(5, 6)          ← main 结束时才析构（不用手写 delete）
```

什么时候**必须**用堆（new / 智能指针）：

- 需要**运行期多态**：容器里存基类指针，指向不同的派生类对象（见 4.3）
- 对象的数量或大小要**运行期才知道**（其实用 `std::vector` 就好，它内部也在堆上）
- 对象要比当前函数**活得更久**：异步任务、回调、长生命周期容器

工程建议：**默认用栈或标准容器（`std::vector`、`std::string`），确实需要延长生命周期或运行期多态时才用堆，并且用 `std::unique_ptr` / `std::shared_ptr`，尽量不裸写 `new` / `delete`。**

### 4.2 重载（overloading）：编译期就决定

**定义**：同一个作用域里，**函数名相同、参数列表不同**（个数、类型或顺序不同），编译器根据你传的实参挑选对应的版本——这个过程发生在**编译期**，叫静态绑定。

```cpp
void print(int v);          // #1
void print(double v);       // #2
void print(const char* s);  // #3
void print(int a, int b);   // #4 参数个数不同，也算重载

print(3);        // 选 #1
print(3.14);     // 选 #2
print("hello");  // 选 #3
print(1, 2);     // 选 #4
```

实测输出：

```text
print(int)         -> 3
print(double)      -> 3.14
print(const char*) -> hello
print(int,int)     -> 3
```

规则与易错点：

- **能构成重载**：参数个数、类型、顺序不同；`const` 成员函数与非 const 成员函数也可以重载。
- **不能构成重载**：只有**返回类型**不同（调用时看不出区别，会报重定义）；只有参数名不同；参数上的顶层 `const`（`void f(int)` 与 `void f(const int)`）被视为同一个函数。
- **构造函数最常重载**：一个类可以提供多种初始化方式，例如 `Vec2()`、`Vec2(double,double)`、`explicit Vec2(double)`。
- **名字隐藏的坑**：派生类里只要声明了同名函数，基类的**所有**重载都会被隐藏；要用 `using Base::print;` 把基类版本引进来。
- 重载决议的顺序大致是：精确匹配 → 类型提升 → 标准转换 → 用户自定义转换 → 可变参数；如果两个候选一样好，就是"歧义（ambiguous）"，编译报错。

### 4.3 虚函数（virtual）：运行期才决定

**定义**：在基类中用 `virtual` 声明的成员函数，允许派生类**重写（override）**；当通过**基类指针或引用**调用时，实际执行的是对象真实类型对应的那个版本——这叫**动态绑定**，靠虚函数表（vtable）实现。

```cpp
struct Shape {
    virtual double area() const = 0;      // 纯虚函数：Shape 变成抽象类
    virtual const char* name() const = 0;
    virtual ~Shape() = default;           // 基类析构必须是虚函数
};

struct Circle : Shape {
    double r;
    explicit Circle(double r_) : r(r_) {}
    double area() const override { return 3.141592653589793 * r * r; }
    const char* name() const override { return "Circle"; }
};

struct Square : Shape {
    double a;
    explicit Square(double a_) : a(a_) {}
    double area() const override { return a * a; }
    const char* name() const override { return "Square"; }
};

std::vector<std::unique_ptr<Shape>> shapes;          // 基类指针的容器
shapes.push_back(std::make_unique<Circle>(1.0));
shapes.push_back(std::make_unique<Square>(2.0));
for (const auto& s : shapes)
    std::cout << s->name() << " 面积 = " << s->area() << "\n";   // 运行期才知道调哪个
```

实测输出：

```text
Circle 面积 = 3.14159
Square 面积 = 4
```

写虚函数时必须知道的几点：

1. **只有通过指针或引用才有多态**。如果参数写成 `void f(Shape s)`（按值传），派生类对象会被"切"成基类部分（对象切片 slicing），虚函数也不再多态。
2. **基类析构函数一定要是 `virtual`**。否则 `delete 基类指针` 时派生类的析构函数不会被调用，派生类自己申请的资源就泄漏了——这是最经典的坑。
3. `override`（C++11）让编译器帮你检查"确实重写了基类虚函数"（写错签名会直接报错）；`final` 表示到此为止、不允许再被重写。
4. **构造函数和析构函数里调用虚函数不会多态**：那时对象还没构造完（或已经开始销毁），只会调用当前层级的版本。
5. **代价**：每个多态对象里会多存一个指向虚函数表的指针（vptr）。实测 64 位 MSVC 下：`sizeof(PlainCircle) = 8`（只有一个 double），而 `sizeof(Circle) = 16`——多出来的 8 字节正是 vptr；此外虚调用多一次间接寻址，通常也无法内联，所以**不需要多态就不要加 virtual**。

### 4.4 一张表总结重载与虚函数

| 对比项 | 重载 overloading | 虚函数 virtual / 重写 override |
| --- | --- | --- |
| 决定时机 | 编译期（静态绑定） | 运行期（动态绑定） |
| 靠什么区分 | 参数列表不同 | 对象的**实际类型** |
| 发生范围 | 同一个作用域内（如同一个类） | 基类与派生类之间 |
| 关键字 | 不需要 | `virtual` / `override` / `final` |
| 典型用途 | 同名函数处理不同类型的参数、构造函数重载 | 多态：同一套接口、不同的实现 |

一句话：**重载看"参数"，虚函数看"对象"；重载在编译期定，虚函数在运行期定。**
